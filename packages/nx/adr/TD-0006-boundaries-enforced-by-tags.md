# TD-0006 — Boundaries are enforced at lint time, by two complementary rules

- **Status:** accepted
- **Date:** 2026-08-09
- **Scope:** `project.json` tags and the root ESLint config (between libraries); each `core` library's own ESLint config (inside a library)

## Context

Architectural rules written only in documentation decay: they are read once, at
onboarding, and every later decision is made under deadline pressure by someone
who remembers them approximately. The rules in this ecosystem — the dependency
matrix, domain isolation, the types-only contracts layer — are precisely the kind
that break silently, because a forbidden import compiles perfectly well.

## Decision

Both boundaries are enforced by lint, each by the mechanism that fits its unit.

**Between libraries — tags.** Every library generated by `@tactical-ddd/nx`
carries tags:

- `scope:shared` or `scope:domain`
- `domain:<name>` for domain libraries
- `type:contracts | core | utils | infrastructure | ui | features`

The root ESLint config maps those tags to `@nx/enforce-module-boundaries`
constraints, and the generators add the per-domain rule when a domain is created,
so a new domain is isolated from its siblings from its first commit rather than
after someone remembers to configure it.

**Inside a library — paths.** Tags describe projects, so they cannot express the
layering within `core`. The `domain` generator therefore writes
`no-restricted-imports` overrides into that library's own ESLint config, scoped
to `src/lib/domain/**` and `src/lib/application/**`, with absolute-path patterns
added when an organization prefix is known. See
[TD-0004](./TD-0004-inward-dependencies-inside-core.md) for what they cover and
what they miss.

`nx lint` is therefore the authority on boundaries in both directions, and the
documentation describes what the lint configs already enforce.

## Rejected alternatives

- **Convention plus code review.** Reviewers catch the imports they happen to
  look at; the rule holds only while the original authors are around.
- **Path-based rules for cross-library boundaries.** They break whenever a
  library moves and cannot express "any other domain's non-contracts library" —
  which is why paths are used only _inside_ a library, where folders are the
  unit and there is nothing else to match on.
- **A custom CI script.** Feedback arrives after the work is finished, and the
  rule lives away from the tool developers already run.

## Consequences for code

- Tags are not a knob to turn. If an import you need is forbidden, the modeling
  is wrong — re-read [TD-0003](./TD-0003-cross-domain-through-contracts.md)
  before touching a tag.
- Never add a new library by hand: it would have no tags, and an untagged library
  is unconstrained — the rule fails open, silently.
- Boundary violations are fixed by moving code or introducing a contract, never by
  an inline `eslint-disable`.
- A `core` library generated with `linter: none` has no layering rules at all —
  the folders are then convention only, and reviews carry the whole weight.
- Neither mechanism can see through a re-export. A barrel that forwards an
  infrastructure symbol turns a blocked import into an allowed one; keep barrels
  to the library's public surface ([TD-0002](./TD-0002-facade-is-the-only-public-surface.md)).

## Signals you are violating it

- A commit changes `tags` in `project.json` and adds an import at the same time.
- An inline disable of `@nx/enforce-module-boundaries` or of
  `no-restricted-imports` anywhere.
- A library whose `project.json` has an empty `tags` array.
- A cross-library boundary expressed as a path pattern instead of tags.
